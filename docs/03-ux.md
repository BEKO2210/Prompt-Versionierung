# Phase 3 — UX / Information Architecture

## 3.1 App structure

```
/                                 Workspace (project list + create)
/p/:project                       Project dashboard
/p/:project/prompts               Prompt list (filter, search)
/p/:project/prompts/:prompt       Prompt tree browser (default view)
/p/:project/prompts/:prompt/v/:version        Version detail
/p/:project/prompts/:prompt/compare?a=&b=     Diff view
/p/:project/prompts/:prompt/runs              Run history (all branches)
/p/:project/prompts/:prompt/refine/:version   Refinement workspace
/p/:project/datasets                          Datasets & test cases
/p/:project/models                            Model profiles
/p/:project/rubrics                           Rubrics
/p/:project/search?q=                         Global search
```

Rationale: `/p/:project` keeps all retrieval scoped and short; every prompt
URL carries its prompt slug so sharing a prompt is one copy-paste. Version
URLs are permanent because versions are immutable.

## 3.2 Navigation system

**Left rail** (always visible inside a project):
- Prompts (default)
- Search
- Runs
- Datasets
- Models
- Rubrics
- Project settings

**Top bar**:
- Project switcher
- Global search box (`Cmd-K`)
- Create button (prompt | test case | model profile | rubric)

**Right inspector** (context-sensitive, collapsible):
- On prompt tree view: selected version's metadata, notes, runs, evals.
- On diff view: the other side's metadata.
- On refinement view: diagnostics list and suggestion preview.

## 3.3 Core screens

### 3.3.1 Prompt tree browser

Primary view of the product.

Layout:
- Left: version tree (collapsible branches, status-coloured nodes).
- Centre: selected version's body with rendered-preview toggle.
- Right inspector: metadata + runs + notes.

Interactions:
- Click a node → select version (URL updates).
- `F` → fork new branch from selected version.
- `E` → create new version (edit) on current branch.
- `C` → add to compare basket; pressing `C` on a second node opens diff.
- `R` → run selected version (opens run dialog).
- `P` → promote (opens promotion dialog with compatibility check).
- `N` → add note.
- `/` → focus search.

Node rendering:
- Colour by status: grey (draft), blue (experimental), purple (candidate),
  green (approved), amber (deprecated), slate (archived).
- Badge for canonical branch head (crown).
- Badge for "has run evidence" (beaker).
- Badge for "has pending suggestion" (sparkle).

Empty state: big "Create first version" CTA with a paste-in template.

### 3.3.2 Version detail

Tabs: **Content** · **Variables** · **Runs** · **Evaluations** · **Notes**
· **Decisions** · **Lineage**.

- **Content**: body with variable highlighting, messages view (if present),
  metadata sidebar (status, parent, branch, numbers, created-by/at,
  change summary, rationale, expected improvement, content hash).
- **Variables**: declared variables, types, defaults, enum values.
- **Runs**: table of runs. Columns: testCase, model, score (aggregated),
  pass/fail, latency, tokens, createdAt. Row → run detail drawer.
- **Evaluations**: grouped by run; criterion breakdown for rubric evals.
- **Notes**: chronological list with kind badges.
- **Decisions**: append-only log.
- **Lineage**: mini-graph showing ancestors and descendants of this
  version with kind-coloured edges.

### 3.3.3 Diff view

Two columns. Top bar shows A and B pickers (any two versions of the same
prompt).

Panels:
- Text diff (monospace, line-level, word-level highlight on modified lines).
- Variable diff (added / removed / type-changed).
- Metadata diff (status, branch, model hint, rationale).
- Run-evidence diff: for each `(testCase, modelProfile)` pair present on
  both sides, show paired scores. This is the *receipts* panel — the
  reason to promote one over the other.

Actions: "Mark preferred" → writes a `PromptComparison` with
`preferredVersionId`.

### 3.3.4 Run dialog / Run detail

Run dialog (invoked from version detail or tree):
- Test case: pick from dataset or "ad-hoc" (free-form bindings).
- Model profile.
- Variable binding form, pre-filled from test case.
- Advanced: temperature override, max tokens override.
- Evaluators to run: multi-select (regex/schema/similarity/rubric/human
  placeholder).

Run detail drawer: rendered prompt, raw output, structured output, tokens,
latency, cost, error, evaluations (with expand for criteria scores).

### 3.3.5 Refinement workspace

Three-pane layout:
- Left: diagnostics list (grouped by severity).
- Centre: current body vs proposed body, diff-highlighted; rationale
  below.
- Right: accept/reject controls; on accept, opens a "commit" form with
  editable change summary and expected improvement.

Selecting a diagnostic scrolls the centre panel to the relevant span.

### 3.3.6 Search

Two modes, visible as tabs:
- **Structured**: filter chips (project, prompt, branch, status, tag,
  model, score range, date range).
- **Natural**: a query string; matches against FTS index; optional
  semantic re-ranking if vector index is configured.

Results: grouped by entity (prompts / versions / runs / notes), each
row shows breadcrumbs (project > prompt > branch > version #).

## 3.4 Critical user flows

### Flow A: first prompt
1. Create project.
2. Create prompt. Name + purpose required; first version form appears.
3. Save → root version (`number=1`) on branch `main`. Status `draft`.
4. Redirect to prompt tree with version selected.

### Flow B: iterate
1. On tree view, press `E` on current head.
2. Edit body; required: change summary. Optional: rationale, expected
   improvement, new status.
3. Save → new version; branch head advances.

### Flow C: branch for an experiment
1. Press `F` on any version.
2. Enter branch name (validated against B2).
3. First edit on the new branch creates version whose parent is the fork
   point.

### Flow D: test and evaluate
1. On a version, press `R`.
2. Pick test case + model profile + evaluators.
3. Run executes (with mock provider, synchronously; with real provider,
   as a background job).
4. Results appear in the Runs tab; evaluations attached.

### Flow E: refine
1. On a version, open Refinement workspace (`/refine/:version`).
2. Diagnostics auto-run on open (cached by `contentHash`).
3. Review diagnostics; for each suggestion, accept or reject.
4. Accepted suggestions create new versions on a new branch
   `refine/<parent-number>-<timestamp>`, with lineage kind `refinement`.
5. Compare and promote.

### Flow F: promote
1. On the candidate version, press `P`.
2. System checks B5 compatibility.
3. If compatible: pointer promotion; otherwise: squashed promotion
   dialog requires confirmation.
4. Decision record written with rationale from a required textarea.

### Flow G: retrieve old prompt
1. `Cmd-K` → type search.
2. Filter by tag or branch; pick a result.
3. Deep-link to that version, showing full context (runs, notes,
   decisions).

## 3.5 Empty states

- No projects: big "Create your first project" with a two-field form.
- No prompts: explanation of prompt-vs-version; CTA to create.
- Version has no runs: prominent "Add evidence: run a test case".
- Prompt has no canonical branch set: banner with "Promote a version"
  CTA (only possible in a rare seed race; service layer prevents
  permanently-unset canonical).

## 3.6 Power-user behaviours

- Full keyboard map surfaced via `?`.
- `g p` → prompts, `g s` → search, `g r` → runs (two-key nav).
- Pasting a URL containing `#version=<id>` into the tree focuses that node.
- Compare basket persists across navigation until cleared.
- All list views support URL-encoded filters (so views are shareable).
